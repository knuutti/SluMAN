# Input display skin editor — plan

A web page SluMAN serves on 127.0.0.1 where a user uploads one PNG holding every asset, draws
rectangles over it to cut out the base, the buttons and the sticks (released and pressed apart),
places them on the base, previews the result with their own controller, and saves a skin that the
Input Display window and the OBS page both load.

## What exists today

- A skin is `controllerskins/<name>/skin.txt` + one sprite sheet (`ControllerSkin.cs`).
  Every line is `part: drawX, drawY, spriteX, spriteY, spriteWidth, spriteHeight`, plus
  `analogPitch` and `imageName`.
- **That's already the editor's model:** "crop a rectangle" sets `spriteX/Y/W/H` and "place it"
  sets `drawX/Y`. The uploaded PNG is the sprite sheet as it is, with no repacking and no
  re-encoding. The editor only writes numbers.
- Renderers: `InputDisplay.cs` (GDI+) and `ObsPad.html` (canvas), served by `ObsPadServer`
  (TcpListener on 127.0.0.1:9674, GET only, routes `/pad`, `/skin.json`, `/skin.png`, `/events`).
  Both draw `base`, then the sticks, then the 14 buttons **only while held**. The released look is
  baked into `base`.
- Sticks: `l3`/`r3` are drawn while the stick is clicked in, `l3Press`/`r3Press` otherwise (the
  names are backwards), offset by `stick * analogPitch`.
- Problems the editor runs into:
  - `InputDisplaySkin` in config.txt stores the skin's **index** in the folder list, so adding a
    skin can change which one is selected.
  - The parser `int.Parse`s every value except `imageName`, so any new non-numeric key throws.
  - Skins live in the app folder only, which an update replaces.

## Decisions

1. **Keep `skin.txt`; extend it in a backward-compatible way.** Add an optional
   `<button>Released` part for each of the 14 buttons (`crossReleased`, `dpadUpReleased`, ...),
   drawn while the button is **not** held. Existing skins don't have them, so they render as they
   do now. An older SluMAN reading a new skin parses the extra lines as ordinary parts and ignores
   them: the skin still works there, just without the released art. Sticks keep their two existing
   keys; the editor shows them as "L stick released / pressed" and maps to `l3Press` / `l3`.
2. **Same server, new routes** on `ObsPadServer` (port 9674) instead of a third port. It already
   serves skins and the live input stream that the editor's preview needs.
3. **User-made skins go to the user data folder** (`UserData.Path("controllerskins")`), so updates
   can't touch them. `SkinNames()` lists the shipped and user folders together. A save may not use
   a shipped skin's name. Editing a shipped skin saves a copy ("DS3 Black (custom)").
4. **The editor is one embedded HTML file** (`SkinEditor.html`, an EmbeddedResource like
   `ObsPad.html`): vanilla JS and canvas, no CDN, so it works offline.
5. **All editing happens in the browser.** The server only lists, serves and saves skins.

## Skin format additions

```
# Released buttons (optional; drawn while the button is not held)
crossReleased: 609, 303, 389, 700, 62, 62
...
```

Render order (both renderers): `base`; then each button's `Released` part when not held or its
pressed part when held, in the existing `buttonParts` order; sticks stay where they are now. Fix the
parser to skip lines it can't parse instead of throwing.

## Server changes (`ObsPadServer.cs`, editor handlers maybe in `SkinEditorApi.cs`)

| Route | |
|---|---|
| `GET /editor` | `SkinEditor.html` (`?skin=<name>` opens an existing skin for editing) |
| `GET /skins` | `[{name, user: bool}]` |
| `GET /skin.json`, `/skin.png` | already there; the editor uses them to load a skin |
| `GET /events` | already there; drives the live preview |
| `POST /skins/save` | JSON `{name, overwrite, analogPitch, parts: {...}, png: <base64>}` |

Save handler:
- Parse headers (the server skips them today) and read the body by `Content-Length`, at most 16 MB.
- **Guard against other web pages:** any site the user visits can send requests to
  127.0.0.1. Require `Host` to be `127.0.0.1:<port>` / `localhost:<port>` (stops DNS rebinding) and
  a custom `X-SluMAN-Editor: 1` header. A cross-site page can't send that header without a CORS
  preflight, and the server never answers `OPTIONS`. Don't send `Access-Control-Allow-Origin: *`
  on the POST.
- Validate: name non-empty, ≤ 64 chars, no `Path.GetInvalidFileNameChars()`, no `..`, not a
  reserved DOS name, not a shipped skin's name. PNG magic bytes. `base` present. Every rect
  starting inside the image and with positive size. (A rect may run past the image's edge: the 17
  DS3 skins' 800 × 558 base is wider than their 784-wide sheet, and the renderers draw the rest
  transparent. Found by the phase 4 round trip.)
- Existing user skin and `overwrite` false → `409` (the page asks, then resends).
- Write `skin.png` + `skin.txt` (generated by `ControllerSkin.Save`, with comments in the
  `defaultSkin.txt` style) to a temp folder, then move it into place.
- On success, raise `ControllerSkin.SkinsChanged`. `InputDisplay` (BeginInvoke to the UI thread)
  reloads its list and, if asked (`select: true`), switches to the new skin, which also moves OBS
  over through `SelectedSkin`.

## Editor page (`SkinEditor.html`)

Layout: parts list on the left, two canvases (**Sheet** and **Layout**) in the middle or as tabs on
narrow screens, a properties panel on the right.

**Load:** drop a PNG, pick one with a file input, or paste one. Or open an existing skin
(`?skin=` / a dropdown from `/skins`), which loads its numbers and sheet.

**Parts list:** Base; D-pad ×4, face ×4, Select/Start, L1/R1/L2/R2, each with **Released** and
**Pressed** slots; L stick and R stick with Released and Pressed slots. Each slot shows set / not set.
Selecting a slot highlights its rect on both canvases.

**Sheet canvas (cropping):**
- Zoom with the wheel, pan with space-drag or middle-drag, pixel grid at high zoom, nearest-neighbour scaling.
- Drag to draw the selected slot's rect. Handles to resize. Arrows nudge 1 px, Shift+arrows 10 px.
- **Snap to sprite:** click a sprite to select the bounding box of the opaque pixels around the
  click (flood fill on alpha > threshold). **Trim:** shrink a rough rect to its opaque pixels. These
  two make cropping fast and exact.
- Every rect already set is shown faintly with its label, so nothing gets cut twice by accident.

**Layout canvas (placing):**
- Canvas = the base rect's size (that's the OBS Browser Source size). The base is drawn at 0,0.
- Drag parts to place them; arrows nudge. Numeric X/Y in the properties panel.
- Placing a part's Pressed slot defaults to the Released slot's position, centred if the sizes
  differ. "Align pressed to released" button.
- "Use same crop as…" for parts that share art (e.g. L1/R1 in the DS3 skins).
- Preview modes: all released, all pressed, **live** (from `/events`, so the user presses their
  real controller), and click a part to toggle it.
- Stick: `analogPitch` slider, with a circle showing how far the stick moves.
- Draw order is fixed (the renderers' order). The page shows it and warns where parts overlap.

**Properties panel:** the selected slot's sprite x/y/w/h and draw x/y as number fields, skin name,
analog pitch, background colour for the preview (matches the Input Display's).

**Undo / redo:** snapshot stack of the layout JSON (small; the image doesn't change).

**Drafts:** the work in progress (layout + image) is kept in IndexedDB, wrapped in try/catch, and
offered back on reopen. The image is too large for localStorage.

**Checks before saving:** errors (block saving): no base, rect outside the image. Warnings (allow
saving): parts with no art at all, parts outside the base canvas (OBS clips them), stick travel
leaving the canvas, a Released slot without a Pressed one or the other way round.

**Save:** name field → `POST /skins/save` → "Saved. Use it now?". Also **Download** `skin.txt` and
the PNG, for sharing or for a SluMAN without the editor. Two files, no zip library.

## SluMAN app changes

- `ControllerSkin.cs`: user skins folder; merged `SkinNames()` and `SkinFolder(name)`; a parser
  that skips bad lines; `Released` parts; `Save(...)`; `IsValidName`; `SkinsChanged` event; select
  the skin **by name** in config.txt (still read an old numeric value once).
- `InputDisplay.cs`: draw Released parts; context menu items **Create Skin…** and **Edit This
  Skin…**, which open the browser (`Process.Start(url)`) at `/editor` (`?skin=<current>`) and
  start the server first if it's off; reload the skin list on `SkinsChanged`.
- `ObsPad.html`: draw Released parts the same way.
- `SluMAN.csproj`: `SkinEditor.html` as EmbeddedResource with a LogicalName.
- `defaultSkin.txt`, README, CLAUDE.md (Input display section), CHANGELOG via release notes.

## Phases

1. ✅ **Format and renderers.** Released parts in both renderers, a parser that tolerates bad lines,
   selection by name, user skins folder. Shippable alone: people can hand-write Released parts.
   Done on `skin-released-parts` (#73).
2. ✅ **Server.** Header parsing, POST with body limit, Host/header guard, `/editor`, `/skins`,
   `/skins/save`, `SkinsChanged` → Input Display refresh. Done on `skin-editor-server`, with:
   - The event is `ControllerSkin.SkinSaved(name, select)`. `Save` itself remembers a `select`
     and sets `ObsPadServer.SelectedSkin`, so it works with no Input Display open.
   - `/events` carries `rev` (`ControllerSkin.Revision`, up on every save). The OBS page loads
     its skin again when it changes, so saving over the skin on screen shows up there too.
   - Portable copies keep user skins in `controllerskins-user` next to the exe, since their user
     data folder is the app folder and shipped and user skins would otherwise share one folder.
   - The save reads the whole body before answering anything: closing a connection with data
     unread resets it on Windows, and the page would get a network error instead of the reason.
     A body over the limit gets its 413 and is read and dropped (up to 4× the limit).
   - Errors are `{ok: false, reason, error}`; `reason` is `forbidden`, `bad-request`,
     `too-large`, `name`, `shipped`, `exists`, `image`, `parts` or `write`, and `error` is a
     sentence for the user.
   - `/editor` serves a stand-in page listing the skins until phase 3 replaces it.
3. ✅ **Editor MVP.** Load PNG, parts list, crop on Sheet, place on Layout, numeric fields, preview
   toggles, save. Done on `skin-editor-page`, with:
   - The Input Display's **Create Skin...** menu item opens `/editor`, switching Serve for OBS on
     first when it's off (one server serves both).
   - A non-PNG image (JPEG, a pasted screenshot) is turned into a PNG in the browser; a PNG is sent
     as it is.
   - Selecting a slot shows that part released or pressed on the layout; Released / Pressed in the
     layout's bar set them all. Clicking a crop on the sheet selects its slot; dragging on empty
     layout pans.
   - A slot cropped for the first time is placed over its other slot (centred), else in the middle
     of the base. "Align with other slot" does the same later.
   - The selected stick shows its movement as a circle; the movement is set under Sticks.
   - The base is always drawn at 0, 0 (its position fields are off).
   - Saving asks before replacing a skin of the same name (the 409), and the page warns before
     closing with unsaved changes.
   - Generated skin.txt leaves out the headings of groups with no parts.
4. ✅ **Editor polish.** Snap-to-sprite and trim, live preview from `/events`, open an existing skin,
   undo/redo, drafts, checks, download, "use same crop as". Done on `skin-editor-polish`, with:
   - Snapping: a click on the sheet selects the smallest crop under it, or, on no crop, crops the
     selected slot to the sprite there (8-connected pixels above alpha 16). Alt+click always crops.
     Trim keeps the part where it's drawn by moving its position by what was cut off.
   - Opening a skin: the header's skin list, `/editor?skin=<name>`, and the Input Display's
     **Edit This Skin...**. Shipped skins open as "<name> (custom)"; a skin's crops aren't pulled
     inside its sheet. Parts SluMAN doesn't draw are left out, and the status says which.
   - Live: `/events` drives the layout (mask bits as `Inputs.Buttons`, sticks moved by
     movement × position); Released / Pressed turn it off.
   - Undo keeps a snapshot from before each change (up to 200); a run of nudges is one step.
   - Drafts: name, parts, movement and PNG bytes in IndexedDB (`sluman-skin-editor`), written
     800 ms after a change and on leaving, offered when the editor opens without a skin, deleted
     on a save.
   - Checks: errors stop the save (no base); warnings (released look without a pressed one, parts
     outside the base or moving out of it) and notes (crops past the sheet's edge, parts with no
     art) don't. Clicking one selects its slot.
   - Download skin.txt is generated in the page exactly as `ControllerSkin.SkinText` writes it.
   - Verified: all 21 shipped skins opened and saved unchanged as copies give the same parts,
     movement and PNG bytes.
5. **Docs and release.**

## Verifying (no automated tests)

- Build, run, right-click the Input Display → Create Skin…
- **Round trip:** open "DS3 Black" in the editor and save it as a copy without changes. The new
  `skin.txt` must have the same numbers as the shipped one, and both renderers must look identical.
- Make a skin with Released parts from a fresh PNG. Check the Input Display window and the OBS page
  (`/pad?skin=<name>`) with a pad attached, sticks included.
- Hostile cases: POST without the header, with a wrong `Host`, a name with `..\`, a non-PNG, a
  20 MB body, overwrite without the flag. Each must be refused with nothing written.
- Load a skin with Released parts in a SluMAN release from before this change: it still renders.
- The editor page can be driven in a browser with Playwright against the running server.

## Open choices (recommended answer first)

- Save to the user data folder vs next to the exe → user data folder (survives updates).
- Same server as OBS vs its own port → same server; Create Skin… turns it on if needed.
- Colour-key tool for PNGs without transparency (re-encodes the PNG with canvas) → later, if asked for.
- "Bake released parts into the base" export for older SluMAN versions → not needed: they ignore
  the new parts, and the released look is simply missing there.
